# 통합 이미지 분석 예제가 남긴 교훈

## 생산자 저장소에서 통합해야 하는 이유

처음에는 `bluetape4k-workshop`에 실전 예제를 두는 방안을 검토했다. 하지만 OCR,
객체 검출, 바코드 판독 계약과 Spring Boot 예제를 실제로 제공하는 곳은
`bluetape4k-image`다. 생산자 저장소에 통합 예제를 두면 세 기능의 현재 API를 같은
빌드에서 컴파일하고, 변경이 생길 때 Examples CI가 즉시 호환성 저하를 발견한다.

워크숍은 완성된 사용법을 소비하는 곳으로 남겨 두고, 생산자 저장소는 기능별
quickstart와 통합 예제를 함께 책임지는 구성이 변경 시점의 어긋남을 줄인다.

## 워크플로 완료와 업무 성공은 다른 축이다

`WorkReport.Success`는 세 작업이 계약대로 끝나고 각 결과 키를 기록했다는 뜻이다.
OCR이 실제 값을 읽었다는 뜻은 아니다. 개별 분석 결과는 `Completed`, `Empty`,
`Unavailable`, `Failed`로 따로 표현해야 한다.

이 둘을 같은 성공 값으로 합치면 한 공급자의 실패가 워크플로 전체 실패가 되고,
정상적으로 얻은 형제 결과까지 잃는다. 반대로 공급자 실패를 빈 결과로 바꾸면
“검사했지만 없음”과 “검사하지 못함”이 같아져 자동 승인 정책이 위험해진다.

## 예상 가능한 실패는 데이터이고 취소는 제어 흐름이다

공급자 미설정, 제한 시간 초과, 공급자 예외는 응답 정책이 판단할 수 있는
`AnalysisResult`다. 그래서 해당 작업은 결과를 기록하고 워크플로 단계 자체는
성공으로 끝낸다.

외부 요청 취소는 다르다. 이를 `Failed`로 바꾸면 이미 연결을 끊은 호출자의 작업이
계속되고, 구조화된 동시성이 깨진다. `TimeoutCancellationException` 중 작업 내부
제한 시간만 `Failed(timeout)`으로 바꾸고, 그 밖의 `CancellationException`은 다시
던져야 한다. Semaphore permit도 성공·실패·제한 시간·취소의 모든 경로에서
반환되는지 검증해야 한다.

## 픽셀 예산은 디코딩 전에 확인한다

압축 파일 크기만 제한하면 작은 파일이 매우 큰 픽셀 버퍼를 만들 수 있다. 따라서
파일 시그니처를 확인한 다음 헤더에서 가로·세로를 읽고, 한 변과 전체 픽셀 예산을
통과한 경우에만 `ImmutableImage`를 만든다.

정상 요청에서는 디코딩을 한 번만 수행하고 같은 불변 이미지를 세 분석 경로가
공유한다. `QualifiedImage`가 원본 `ByteArray`를 보관하지 않는 것도 중요하다.
그렇지 않으면 동시 요청마다 압축 바이트와 디코딩 픽셀 버퍼가 함께 오래 살아남는다.

## 코루틴 제한 시간만으로 네이티브 호출을 죽일 수는 없다

`withTimeout`은 협조적인 suspend 작업에는 유효하지만, 이미 시작된 네이티브 함수가
thread interruption에 반응하지 않으면 즉시 종료시키지 못한다. Semaphore는 새
호출의 수를 제한할 뿐 이미 실행 중인 네이티브 함수를 강제로 끝내지 않는다.

엄격한 종료 시간이 필요한 공급자는 별도 프로세스나 원격 worker로 격리하고,
프로세스 단위 제한 시간과 종료 정책을 가져야 한다. 이 예제의 `native-ocr` 프로필은
그 경계를 README에 명시하고 기본 CI에서는 실행하지 않는다.

## 검증 근거와 다음 변경의 가드

- 새 예제의 clean test 48개가 통과했다.
- 영향 모듈 7개의 테스트는 실패 0건으로 통과했다.
- 집중 테스트 20개가 단일 디코딩, 디코딩 전 거부, 병렬 실행, 동시 실행 상한,
  permit 복구, 부분 결과, 외부 취소를 검증했다.
- `detekt`, `actionlint`, 다이어그램 검사, 상대 링크 검사와 `git diff --check`를
  최종 게이트로 사용했다.
- multipart 파일 한도와 전체 요청 한도를 같게 두지 않는다. 전체 요청 한도에는
  multipart envelope가 들어갈 여유가 있어야 하며 회귀 테스트가 이를 고정한다.
- 앞으로 분석 경로를 추가할 때는 고유한 `WorkContext` 키, 독립 timeout과
  Semaphore, `Empty`/`Failed` 구분, 외부 취소 재전파를 함께 추가해야 한다.
