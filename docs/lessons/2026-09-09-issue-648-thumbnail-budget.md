# #648 변환 전 입력·출력 픽셀 예약

## 원인과 결정

입력 크기만 검사하고 예약하면 작은 이미지의 확대 출력이 단일·동시 픽셀 한도를
우회한다. 입력과 요청 출력은 각각 `maxPixels`로 검사하고, 두 크기의 합이
`maxInFlightPixels`를 넘으면 변환 전에 거부한다. 기존 `PixelPermitLimiter`를
재사용하되 이 호출 경계에서 초과 요청을 먼저 거부하여 limiter의 기존 clamp 계약은 유지했다.

예약은 decode 직전부터 쓰기 종료까지 유지한다. 실패·취소에는 기존 반환 경로를
사용한다. 이 값은 픽셀 가중치이며 encoder·crop 임시 메모리나 호출자가 결과로
보관하는 이미지까지 포함한 전체 heap 한도는 아니다.

## 회귀 증거와 다음 검증 기준

5×5 입력으로 100×100 출력과 입력·출력 합계 초과를 검사했다.
수정 전 세 회귀가 실패했고, permit을 입력 전용으로 되돌린 mutation에서도
동시 writer가 2개에 도달해 예상 상한 1을 위반했다. 따라서 최종 결과 크기만
검사하지 말고 실제 write 단계의 동시 진입과 실패·취소 후 반환을 함께 검증한다.

writer 내부 진입·해제 신호가 필요해 범용 stress tester 대신 제한 시간 있는
래치를 사용했다. 이는 특정 회귀의 재현이며 스케줄러 전체나 heap 상한의 증명은 아니다.
실제 job 취소 후 failure callback과 결과 파일이 생기지 않는지도 확인한다.

probe와 decode 사이 파일이 바뀌면 이미 큰 입력을 할당한 뒤일 수 있다.
실제 decode 크기가 예약량보다 크면 transform 전에 거부하지만 이를 원자적
snapshot으로 설명해서는 안 된다. 처리 중 원본을 변경하지 않는 전제를 문서화했다.

## 작업 중 바로잡은 가정

- PNG writer에 없는 `Default`를 가정한 첫 테스트는 컴파일 오류였다.
  실제 `MaxCompression`을 확인한 뒤 얻은 행동 실패만 RED로 인정했다.
- 다른 저장소에서 쓰는 `apiCheck` 태스크를 가정해 실행이 실패했다.
  이 저장소의 `checkProductionAbi`를 사용하며, 다음에는 이전 성공 명령이나
  실제 태스크 등록을 확인한다.
- 기준 소스도 detekt 경고가 있었다. 같은 설정으로 정확한 기준 blob을 검사하여
  기준 5건·수정 4건을 구분했다. 신규 경고가 없다는 사실은 전체 정적 검사 통과가 아니다.

독립 리뷰에서 드러난 Builder 목록 별칭은 #649에서 수정한다.
`process()` 재수집 시 중복 경로 상태가 남는 문제와 호출 간 limiter 분리는
기존 수명 계약의 별도 P2 위험이며 이번 픽셀 산술 수정에 섞지 않는다.
