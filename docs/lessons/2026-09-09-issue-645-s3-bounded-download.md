# S3 다운로드 크기는 읽는 중 제한한다

## 배경과 원인

이슈 #645의 byte-array 다운로드는 HEAD 크기를 검사한 뒤 `downloadBytes`로 전체 본문을
적재했다. HEAD 이후 객체가 바뀌면 사후 검증 전에 메모리를 과도하게 사용할 수 있었다.

## 결정

기존 `S3Operations.resource`와 이미 의존 중인 `bluetape4k-io.readAllBytes(maxBytes)`를
재사용한다. 이 함수는 초과 판정을 위해 최대 한 byte를 추가로 읽고 부분 결과를 반환하지 않는다.
호출자가 스트림을 `use`로 닫고 예외를 기존 이미지 저장소 계약으로 변환한다.

다른 S3 bounded API는 별도 최대 크기와 예외 계약을 가지므로 이름만 보고 대체하지 않는다.
새 의존성이나 별도 버퍼 관리 구현은 추가하지 않는다. HEAD와 GET의 동일 크기 객체 교체까지
탐지하는 변경은 이 이슈 범위가 아니며, blocking read timeout은 S3 client가 담당한다.

## 검증

변경 전 Spring 모듈 210개 테스트가 통과했다. 무한 입력을 모사한 회귀 테스트는 수정 전
읽은 byte 수가 0이라 실패했고, 수정 후 상한 4에 대해 5 byte만 읽고 스트림을 닫았다.
정확한 상한, 읽기 실패, 취소 전파와 스트림 종료도 회귀 테스트로 보호한다.

## 이후 변경 시 확인할 사항

HEAD 사전 검사와 읽기 중 상한 검사, HEAD에서 확인한 크기와의 비교를 각각 유지한다.
크기 제한은 무할당 보장이 아니다. 결과 조립 중 실제 본문의 약 두 배 메모리가 필요하다.

독립 리뷰에서 `resource` 생성 계측과 실제 GET 계측이 다름을 확인했다. 재사용 시에는
반환 타입뿐 아니라 장식자의 계측 범위와 취소 시점도 비교한다. 이미지 저장소 계측을
함께 사용하는 성공·실패 테스트로 전체 다운로드 측정 경로를 보호한다.

기본 `detekt` 작업은 `NO-SOURCE`였다. 분석 성공을 주장하지 않고 실제 모듈 소스를 지정해
기준 커밋과 비교했으며, 기존 경고 43개가 동일했다. 분석 결과는 작업 종료 코드만이 아니라
입력 파일과 신규 경고 유무로 검증한다. 코루틴 취소 테스트는 예외 객체 동일성을 요구하지
않고 타입·메시지와 작업 취소, 자원 종료를 확인한다.
